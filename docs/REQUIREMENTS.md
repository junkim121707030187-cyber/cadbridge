# 요구사항과 추적
근거 U는 이번 사용자 제공 합의 원문이다. H는 사용자가 제공한 2026-10-12 M3 조사 요약이며 이번 직접 소스 열람·재실행이 아니다. P는 문서상 엔지니어 제안으로 승인·구현 사실이 아니다. 자세한 출처는 [상태·근거](STATUS_AND_EVIDENCE.md)를 따른다.

## 일곱 개념별 정리
| 개념 | 이미 합의한 것(U) | 과거 정의(H) | 남은 결정 | 엔지니어 확인 |
|---|---|---|---|---|
| 요구사항·명세·완료 조건 | native 편집, 단방향 첫 성공 | 제한 STEP·편집 사례 | CAD쌍·부품·공차 | 실제 저장·재열기·편집 가능성 |
| 모듈화·데이터 모델·인터페이스 | 개별 부품부터 맥락 이전 | 관측→IR→제약→형상 | 지원 기능 범위 | native API·손실·단위·버전 호환 |
| 컨텍스트 엔지니어링 | 사실·요구·가정 구분, 작업 맥락 보존 | 로컬 프로젝트·이력 | 보존·공유 세부 정책 | 출처 추적·연결·복구 |
| 점진적 개발·버전 관리 | 단계적으로 확장 | 저장·재개 코드 존재 보고 | 원격·협업 승인 정책·일정 | 소스 회수·해시·재현 환경 |
| 테스트·디버깅·관찰 가능성 | 실행과 의도 판정 분리 | 329와 87 별도 기록 | 판정 수치·벤치마크 | native 관문·거부 사례·로그 |
| 권한·신뢰 경계·강제 장치 | 중요 조건 보호·모호성 선택·대체 공개 | IR 검사 등, run 자동 선택 경로 | 자동 대체 범위·UI·인증 | 실행 차단·승인 주체 검증 |
| 유지보수성·기술 부채·이해 부채 | 기업·팀 대상 | 제한 지원·미지원 거부 | 유지보수 주체·장기 지원 | 어댑터 비용·라이선스·설명 가능성 |

## 테스트 가능한 요구
아래는 제품 요구이며 현재 통과한 시험 목록이 아니다. 관문 G와 시험 V의 정의는 [VALIDATION](VALIDATION.md)에 있다.

| ID | 요구·수용 기준 | 근거 | 검증 연결 |
|---|---|---|---|
| R-01 | STEP 입력으로 native 피처·스케치·치수·제약을 생성하고 지정 편집을 수행한다 | U2,U4 | G1,V-N |
| R-02 | 서로 다른 오픈소스 CAD A→B에서 부품 수신·수정·저장을 완료한다 | U2,U3 | G2,V-N |
| R-03 | 트리 동일성·유일 의도 복원을 보장하지 않고 추정과 확인 사실을 구분해 표시한다 | U4,U6 | V-I,V-C |
| R-04 | 시작 프롬프트에서 필수 설계 조건·수정 금지 부분을 받고 위반 실행을 차단한다 | U7 | V-P |
| R-05 | 의도가 모호하면 후보·근거·편집 차이를 제시하고 사용자 선택 전 실행을 보류한다 | U8 | V-I,V-P |
| R-06 | 기능 차이 대체는 허용 정책 내에서만 실행하고 변경 내용·영향을 표시한다 | U9 | V-P,V-C |
| R-07 | AI 작업에 사용한 컨텍스트를 해당 부품·설계버전·결과에 연결해 재조회한다 | U5,U6 | V-C |
| R-08 | 원본 확인·기하 측정·사용자 요구·AI 가정을 출처와 함께 구분한다 | U6 | V-C |
| R-09 | 실패 시 원본과 마지막 유효 상태를 보존하고 미지원·검증 실패를 명시한다 | H 보호,P 확장 | V-F |
| R-10 | 단순 형상 일치와 native 편집·의도·권한·컨텍스트 통과를 별도로 보고한다 | U1,H 시험 구분 | G1,G2,V-G |
| R-11 | 공차 종류·단위·적용 대상·수치·판정법이 확정되기 전 최종 합격을 선언하지 않는다 | U6,H 공차 | V-G |
| R-12 | 실제 승인 주체·대상 버전·행위를 검증하며 문자열·로컬 해시를 인증으로 쓰지 않는다 | H 인증 한계,P 강제 | V-P |

U 번호는 사용자 최신 합의 1~12의 번호다. H 기반 확장 요구 R-09와 R-12의 구체 강제 방식은 제안이며 보안 설계 검토가 필요하다. 기술 JSON 필드·어댑터 함수·시험 코드는 엔지니어가 정한다. 사용자에게는 보호 조건·대체 허용·제품 판정 등 제품 결정을 요청한다.
