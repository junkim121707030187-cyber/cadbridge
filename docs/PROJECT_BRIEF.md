# 제품 개요
현재 첫 구현 범위·실측은 [MVP 계획](MVP_PLAN.md)과 [상태](STATUS_AND_EVIDENCE.md)를 따른다. 아래 준비 단계 설명은 당시 산출물이며 전체 제품 완료를 뜻하지 않는다.

기준: [요구사항](REQUIREMENTS.md) · [결정 로그](DECISIONS.md)

## 대상과 문제
기업체와 팀 프로젝트 사용자는 CAD 프로그램·버전 차이 때문에 다른 사람의 설계를 자기 환경에서 수정하고 변경 맥락을 이어가기 어렵다. 장기 목표는 설계 파일뿐 아니라 변경 이력과 AI 작업 컨텍스트를 함께 다루는 협업 워크스페이스다.

## 단계별 범위
| 단계 | 결과 | 범위 경계 |
|---|---|---|
| 준비 | 요구·정책·검증 관문 문서 | 이번 산출물; 구현 없음 |
| 1 | STEP에서 오픈소스 CAD의 피처·스케치·치수·제약을 가진 native 부품 재구성 | 개별 부품, 지원 형상은 조사 후 정의 |
| 2 | 오픈소스 CAD A의 부품을 다른 오픈소스 CAD B에서 받아 수정·저장 | 서로 다른 CAD 프로그램 두 개; 라이브러리 두 개로 대체 불가 |
| 후속 | 프로젝트 맥락·이력·조립체·다인 협업 확장 | 별도 명세와 완료 조건 필요 |

첫 성공 장면은 A의 사용자가 만든 부품을 B의 사용자가 자기 CAD에서 받아 수정하고 저장하는 것이다. 왕복 협업·동시 편집·자동 병합은 첫 완료 조건이 아니다. 파일 열기나 형상 변환만으로 최종 제품 성공을 선언하지 않는다.

## 재구성 원칙
원본을 해체·분석해 확인 가능한 작업 과정과 설계 의도를 파악하고 LLM이 대상 CAD의 유사한 피처·제약을 계획한다. 원본 트리 이름·순서의 동일성이나 STEP에서 소실된 의도의 유일 복원은 보장하지 않는다. 모호한 의도는 후보·근거·편집 방식 차이를 제시해 사용자가 선택한다.

## 현재 비범위와 미정
상용 CAD native 연동, 조립체 관리, Git 분기·병합 제품 기능은 첫 단계에 포함하지 않는다. 대상 CAD쌍·버전, 지원 부품 집합, 일정, 공차, 비용·재시도, 권한 UI, 유지보수 주체·지원 정책은 미정이다. [검증](VALIDATION.md)과 [작업 보드](TASK_BOARD.md)에서 선정과 증거 확보를 관리한다.
